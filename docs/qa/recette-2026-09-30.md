### `passe-debutant.test.ts` : « écart 15,5 > 12 » (gravité 2, corrigé)

Cause : après une passe du joueur, Pomme estime les pierres mortes pour choisir le « trou » à fermer (`chooseMoveDetail`, `src/engine/simple.ts`). Cette estimation s'arrêtait après **150 ms** au lieu d'un nombre fixe de simulations. Quand la machine est chargée (suite Vitest complète en parallèle, CI, ou vrai téléphone lent), elle fait moins de simulations, juge d'autres pierres mortes et ferme un autre trou.

Preuve : une horloge simulée lente (2 ms par lecture) rejoue le cas « 40 coups, graine 2 ». Horloge rapide : Pomme joue C8 (11) puis passe, écart −0,5 → 4,5. Horloge lente : Pomme joue E7 (22) puis passe, écart −0,5 → 15,5, soit 16 points de plus. C'est le chiffre signalé.

Ce n'est pas qu'un défaut de test : sur un téléphone lent, Pomme profite plus des passes du débutant que sur un ordinateur, ce que #235 voulait éviter.

Correctif : ces pierres mortes sont estimées avec `ESTIMATION_GAIN` (400 simulations, plafond de 1,5 s), comme `coupQuiRapporte` juste à côté. Mesuré sur la machine de recette : 70 ms en 9 × 9, 300 ms en 19 × 19. On ne paie ce temps qu'après une passe ou quand une frontière reste ouverte. Nouveau test `src/engine/passe-debutant-lent.test.ts` : rouge avant (`[22, -1]` au lieu de `[11, -1]`), vert après. `src/engine` et `src/go` : 46 fichiers verts.

Hors périmètre : `src/engine/simple.ts` appartient à l'agent moteur-go.

### Garde-fou ajouté : test du contrat client ↔ serveur

`src/data/contrat-serveur.test.ts` (29 tests, dans `npm test`, donc en CI) lit le code du client et vérifie, sans réseau :

1. chaque `db.rpc('nom', { args })` du client correspond à une fonction `public.nom` des migrations, avec **les mêmes noms d'arguments** (PostgREST trouve la fonction par ces noms) et un `grant execute … to authenticated` ;
2. chaque `functions.invoke('slug')` a son dossier dans `supabase/functions` ;
3. chaque action envoyée à `game-action` (`move`, `propose_dead`, `accept`, `resume`, `defi_coup`) est acceptée par les analyseurs du serveur (`parseActionRequest`, `parseDefiCoupRequest`), et `index.ts` aiguille bien `defi_coup` ;
4. chaque RPC appelée par les fonctions serveur (`jouer_coup_defi`, `finish_game_by_score`) existe dans les migrations ;
5. chaque table lue ou écrite par le client existe, a la RLS activée et une politique **permissive** pour chaque opération (`upsert` = insert + update) ;
6. chaque table écoutée en temps réel est dans `supabase_realtime` et lisible ;
7. les e2e ne simulent aucune RPC ni fonction serveur absente du dépôt.

Contrôle : en renommant `p_jeton` en `p_token` dans `src/data/defi.ts`, le test échoue avec « arguments de rejoindre_defi : expected [ 'p_token' ] to deeply equal [ 'p_jeton' ] ».

Limite : ce test compare le client **au dépôt**. #344 venait d'un écart entre le dépôt et **la production** : il faut aussi la vérification suivante.

### Proposé : vérifier le déploiement (à confier à l'architecte)

Un job de CI sur `main` (et avant chaque déploiement Vercel de production), avec un jeton de la Management API Supabase en secret GitHub, en lecture seule :

1. **Fonctions** : `GET /v1/projects/{ref}/functions`. Chaque dossier de `supabase/functions` doit être déployé, avec une date de mise à jour postérieure au dernier commit qui touche ce dossier (`git log -1 --format=%ct -- supabase/functions/<slug>`). Sinon, échec : « game-action : dépôt modifié le …, déployé le … ».
2. **Migrations** : `GET /v1/projects/{ref}/database/migrations` (point d'accès à confirmer). Chaque fichier de `supabase/migrations` doit y être par son **nom**. Tant que les versions diffèrent, on compare les noms. Mieux : appliquer désormais les migrations avec leur version de fichier (`supabase db push`), et réaligner une fois la table `supabase_migrations.schema_migrations` sur les noms de fichiers du dépôt.
3. **Ordre de déploiement** : fonctions et migrations d'abord, front ensuite. Vercel ne publie en production qu'après ce job vert (« Required checks » ou `vercel deploy --prod` dans la CI).
4. **Test de fumée après déploiement** : appeler `game-action` avec une action inconnue et un jeton anonyme de test. Attendu : `400 format`, jamais `404` (fonction absente) ni `500 configuration`. Ajouter les tests SQL (`bash supabase/tests/lancer.sh`, Postgres 16) à la CI.
